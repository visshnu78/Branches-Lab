1. Executive Summary & Elevator Pitches

"Branches Lab is a full-stack digital innovation hub platform that I transformed from a static landing page into an interactive, database-backed web application. 2. System Architecture & Tech Stack Justifications

Interviewers frequently ask: "Why did you choose this specific tech stack over alternatives?" Here is the exact technical rationale:

Layer Technology Why Chosen (Interview Rationale)
Backend Runtime Node.js + Express.js Event-driven, non-blocking I/O model is ideal for I/O-heavy RESTful APIs. Keeps the codebase in a single language (JavaScript) across the entire stack, eliminating context switching.
Database & ORM Prisma ORM + SQLite / PostgreSQL Prisma provides compile-time type safety, declarative schema modeling, and automated migrations. SQLite gives zero-config portability locally, while a single environment variable change (DATABASE_URL) targets PostgreSQL in production.
Authentication JWT + bcryptjs Stateless JSON Web Tokens enable decoupled architecture without server-side session stores. Passwords are securely hashed with bcrypt using 10 salt rounds to defend against rainbow table attacks.
Security Helmet, CORS, express-rate-limit Mitigates OWASP Top 10 risks: Helmet sets protective HTTP headers, CORS restricts unauthorized cross-origin requests, and rate-limiting defends against brute-force and DDoS attempts.
Frontend Vanilla JS (ES6+) + CSS Tokens Delivers an ultra-lightweight bundle (<15KB) with zero build-tooling friction and instantaneous rendering, demonstrating deep mastery of foundational DOM APIs without relying on heavy frameworks.

3. Deep Dive: Key Features & Engineering Challenges

✨ Feature 1: Interactive Project Intake Modal

Challenge: Avoid page reloads and provide immediate feedback on project inquiry submissions.

Solution: Created a decoupled modal controller (modal.js) managing background scroll locking, input sanitization, dynamic service pre-selection, and asynchronous POST /api/inquiries dispatch with loading states and toast notifications.

🔍 Feature 2: Real-time Search & Filter

Challenge: Live filtering on every keystroke can cause DOM thrashing and UI stuttering.

Solution: Implemented a 250ms debouncing mechanism in services.js. The filter engine computes an intersection of active category pills and case-insensitive keyword queries, smoothly animating matching cards or displaying an empty state.

🌙 Feature 3: Persistent Dark/Light Mode

Challenge: Preventing Flash of Unstyled Content (FOUC) while respecting both OS settings and user choice.

Solution: Built theme.js with CSS custom property tokens. It checks localStorage first, falls back to window.matchMedia('(prefers-color-scheme: dark)'), and binds a live listener to system preference changes.

🛡️ Feature 4: Resilient Client API Layer

Challenge: Demonstrating the frontend if the backend server is offline or not yet booted.

Solution: Designed an intelligent client API wrapper (api.js) that tests /api/health with an AbortController timeout. If the backend is unreachable, it seamlessly routes CRUD actions to a simulated localStorage mock database.

4. Database Schema & Data Modeling (Prisma)

The application models core business domain entities with explicit relations and validation:

// User Model: Role-based access control (CLIENT vs ADMIN)
model User {
  id           String    @id @default(uuid())
  email        String    @unique
  passwordHash String
  name         String
  role         String    @default("CLIENT") // "CLIENT" | "ADMIN"
  inquiries    Inquiry[]
  createdAt    DateTime  @default(now())
}

// Inquiry Model: Project proposals submitted by clients
model Inquiry {
  id          String   @id @default(uuid())
  clientName  String
  email       String
  serviceType String
  budget      String
  timeline    String
  details     String
  status      String   @default("PENDING") // "PENDING" | "IN_REVIEW" | "ACCEPTED"
  user        User?    @relation(fields: [userId], references: [id])
  userId      String?
  createdAt   DateTime @default(now())
}

// Service Model: Dynamic service offerings with slug indexing
model Service {
  id          String   @id @default(uuid())
  title       String
  slug        String   @unique
  category    String   // "STRATEGY" | "DESIGN" | "ENGINEERING" | "AI_DATA" | ...
  description String
  icon        String
  featured    Boolean  @default(false)
}

5. Top 10 Technical Interview Questions & Model Answers

Q1: Walk me through what happens under the hood when a user submits an inquiry.
"When the user clicks 'Submit Proposal', modal.js intercepts the event and runs client-side validation. If valid, the button enters a loading state and dispatches an asynchronous fetch request to POST /api/inquiries. On the server, the request passes through Helmet, CORS, and rate-limiting middlewares, then enters validateInquiry to verify email format and text lengths. The route handler calls prisma.inquiry.create(), storing the record in SQLite. The server responds with HTTP 201 Created and JSON payload. The client receives the response, resets the form, triggers a slide-in green toast notification, and closes the modal after 1.5 seconds."
Key Talking Points: Event interception, validation, middleware pipeline, ORM persistence, HTTP status codes, UI state feedback.
Q2: How does authentication and authorization work in this project?
"I implemented stateless authentication using JSON Web Tokens (JWT). When a user registers or logs in via /api/auth/login, their password is verified against the stored hash using bcryptjs.compare(). Upon verification, the server generates a signed JWT containing the user's ID, email, and role (such as 'ADMIN'), with a 7-day expiration. On protected routes, the authenticateToken middleware extracts the Bearer token from the Authorization header and verifies the signature using jwt.verify(). For administrative actions, a second middleware, requireAdmin, checks the decoded role and blocks non-admins with 403 Forbidden."
Key Talking Points: Stateless JWT, bcrypt salt hashing, Bearer auth header, middleware chaining, 401 vs 403 status codes.
Q3: Why and how did you implement debouncing on the search input?
"Without debouncing, every single keystroke triggers filter calculations and DOM modifications, which causes performance lag and unnecessary re-renders. I implemented a 250ms debounce function using clearTimeout and setTimeout. When the user types, any pending timeout is cleared, and a new timer starts. The filtering logic only executes once the user pauses typing for 250ms. This keeps typing fluid and responsive while keeping CPU utilization low."
Key Talking Points: Event throttling vs debouncing, DOM performance, JavaScript timers, user experience.
Q4: How did you design the application for security?
"I followed defense-in-depth principles: 1. HTTP Headers: Used helmet to protect against cross-site scripting (XSS), clickjacking, and MIME-type sniffing. 2. Rate Limiting: Configured express-rate-limit to limit clients to 150 requests per 15-minute window, mitigating brute-force and DoS attacks. 3. CORS: Enforced an origin allowlist to prevent unauthorized domains from querying the API. 4. Credential Protection: Passwords are never stored in plaintext; they are hashed with bcrypt (10 rounds). 5. SQL Injection Defense: By using Prisma ORM with parameterized queries, SQL injection vulnerabilities are eliminated by default. 6. Error Sanitization: Centralized error middleware ensures detailed stack traces are never exposed in production."
Key Talking Points: Defense-in-depth, OWASP Top 10, parameterized queries, Helmet, rate limiting.
Q5: Why did you choose Vanilla JS over React, Vue, or Angular?
"For a high-conversion landing page and hub, speed is paramount. Frameworks like React introduce 100KB+ of bundle overhead, hydration delays, and complex build tooling. By using modern Vanilla ES6+ JavaScript, the entire client footprint is under 15KB, loads in milliseconds, and has zero build dependencies. Furthermore, building this in Vanilla JS allowed me to demonstrate strong mastery of core browser fundamentals—such as the DOM API, IntersectionObserver, Fetch API, and Event Listeners—which form the bedrock of any modern frontend framework."
Key Talking Points: Performance budget, First Contentful Paint (FCP), core JavaScript fundamentals, framework tradeoffs.
Q6: How does the dark mode implementation prevent a Flash of Unstyled Content (FOUC)?
"FOUC occurs when JavaScript applies the theme class after the DOM has already rendered in default light mode. To prevent this, the theme script reads localStorage immediately and assigns the data-theme='dark' attribute directly to document.documentElement at the earliest possible stage. All theme colors are defined as CSS custom properties (variables) on :root and overridden under [data-theme='dark'], allowing instant, flicker-free repaints."
Key Talking Points: Critical rendering path, CSS custom properties, DOM lifecycle, FOUC prevention.
Q7: What is the benefit of using Prisma over traditional query builders or raw SQL?
"Prisma provides three major benefits: 1. Declarative Schema: The schema.prisma file serves as the single source of truth for database models, making relationships transparent. 2. Type-Safe Client: The generated client provides auto-completion and compile-time error detection, drastically reducing runtime bugs. 3. Database Portability: Developing locally on SQLite requires zero installation or database services, while switching to production PostgreSQL only requires changing the provider and connection string."
Key Talking Points: Developer experience, type safety, automated migrations, database portability.
Q8: How would you scale this architecture if traffic grew 100x?
"To scale to hundreds of thousands of users, I would: 1. Database: Transition from SQLite to managed PostgreSQL with connection pooling (e.g., Prisma Accelerate or PgBouncer) and read replicas. 2. Caching: Introduce Redis to cache frequent queries such as GET /api/services. 3. Stateless Horizontal Scaling: Since our Express backend uses stateless JWTs, we can deploy multiple instances behind an Nginx or AWS ALB load balancer. 4. Static Asset CDN: Offload the HTML, CSS, and JS assets to Cloudflare or AWS CloudFront for global edge caching."
Key Talking Points: Horizontal scaling, Redis caching, connection pooling, CDN edge distribution.
Q9: What was the most challenging bug you encountered and how did you resolve it?
"One interesting challenge was handling port collision and background process lifecycle on Windows, where port 5000 was held by an orphaned Node process. I used PowerShell network diagnostic cmdlets (Get-NetTCPConnection and Win32_Process) to track the owning PID, analyze the process command line, and gracefully terminate it before binding the server. Additionally, designing the offline mock fallback required careful handling of asynchronous timeouts using AbortController so the user wouldn't experience a 10-second freeze when the backend was unreachable."
Key Talking Points: System diagnostics, PID management, AbortController, resilient UX under failure.
Q10: If you had another two weeks to work on this, what would you add next?
"I would implement: 1. Admin Dashboard: A protected frontend portal where administrators can view all incoming project proposals, filter by budget/status, and update inquiry statuses (e.g., 'IN_REVIEW', 'ACCEPTED'). 2. Automated Email Notifications: Integration with Nodemailer or SendGrid to send automatic email confirmations to clients upon submission. 3. Automated Testing: End-to-end testing with Playwright and unit/integration tests with Jest and Supertest."
Key Talking Points: Product vision, test automation (Jest/Playwright), transactional email, continuous improvement.
